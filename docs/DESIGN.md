# Nana — детальный технический дизайн

Статус: черновик для обсуждения. Правим до начала реализации.

### Целевые метрики

- Время до первого звука: **p50 ≤ 1.5 с, p95 ≤ 2.5 с** (разговор без инструментов)
- То же с вызовом инструмента: **p50 ≤ 2.5 с** (маскируется голосовой преамбулой)
- Быстрый путь (локальные команды): **≤ 500 мс**
- Wake-word: FRR < 5 % при FAR < 0.5 срабатываний в час на реальном комнатном шуме
- Тишина после реплики пользователя никогда не длится дольше 2.5 с (сторож с фразой-заполнителем)

## 2. Что поменяли ответы заказчика

**Все четыре группы возможностей сразу.** Инструменты перестают быть поздней фазой — они определяют архитектуру с первого дня. Вызов инструмента через LLM стоит двух round-trip до модели, то есть +0.8–1.5 с. Отсюда два следствия: локальный быстрый путь для частых команд и голосовая преамбула, маскирующая работу инструмента.

**Управление ПК и умным домом.** Голос — неаутентифицированный канал. Команду может подать любой человек в комнате, реклама по телевизору или колонка соседа. Нужна модель разрешений, а generic-инструмент «выполни shell-команду» не появляется в системе никогда.

**Таймеры.** Требуют инициативной речи: Nana должна заговорить без запроса. Это отдельный канал в архитектуре со своей очередью и политикой прерывания.

**Окно продолжения 8 с.** Появляется состояние, в котором микрофон активен без wake-word. Нужна защита от случайной речи в комнате.

**Профиль и история.** SQLite, стратегия извлечения контекста и — важное — извлечение фактов строго вне горячего пути.

### 3.2 Машина состояний

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
     [Idle] ──wake-word──► [Verify] ──ок──► [Listening] │
        ▲                     │ нет               │     │
        │                     └──────────┐        │ endpoint
        │                                │        ▼     │
        │                                │   [Thinking] │
        │◄── таймаут 8 с ──┐             │        │     │
        │                  │             │        ▼     │
        │            [Continuation]◄─────┼─── [Speaking]│
        │                  │             │        │     │
        │                  └─речь─► [Listening]   │     │
        │                                    barge-in───┘
        │
        └──◄── [Proactive] ◄── таймер/событие
```

Правила переходов:

- `Idle → Verify`: детектор wake-word сработал. Забираем 1.5 с pre-roll и прогоняем через ASR, чтобы подтвердить наличие фразы. Стоит ~150 мс, но отсекает большинство ложных активаций. Отключается флагом для быстрого режима.
- `Verify → Listening`: фраза подтверждена. Если в pre-roll после имени уже есть команда («Хей Нана, какая погода») — она не теряется, идёт в ASR целиком.
- `Listening → Thinking`: сработал endpointing (см. 4.3).
- `Speaking → Listening`: barge-in (см. 4.5).
- `Speaking → Continuation`: воспроизведение закончилось. Таймер 8 с.
- `Continuation → Listening`: VAD зафиксировал речь длиннее 400 мс. Дальше — проверка адресности (см. 4.6).
- `Continuation → Idle`: таймаут.
- `Proactive`: может вклиниться из `Idle` немедленно; из `Listening`/`Thinking`/`Speaking` — встаёт в очередь.

### 3.4 Аудиоэндпоинты и топология

**Решение:** первым делаем десктопный эндпоинт — системный микрофон по умолчанию и текущее устройство вывода (наушники или колонки). Многокомнатная схема с множеством микрофонов и динамиков планируется дальше.

#### Почему это выбор архитектуры, а не просто «первый вариант»

Раз в будущем эндпоинтов много, `nanad` не должен владеть *микрофоном* и *динамиком*. Он владеет **множеством эндпоинтов**:

```rust
pub trait Endpoint: Send + Sync {
    fn id(&self) -> EndpointId;
    fn capture(&self) -> Receiver<AudioFrame>;
    fn playback(&self) -> Arc<dyn AudioSink>;
    fn aec_mode(&self) -> AecMode;   // Off для наушников, Full для колонок
    fn presence(&self) -> Presence;  // активность пользователя на этом эндпоинте
}
```

Каждый эндпоинт несёт свой VAD, свой детектор wake-word и своё состояние AEC. **Сессия привязана к эндпоинту:** имя услышано на X — ответ звучит на X.

Если этого не заложить сейчас, демон захардкодит один поток захвата и один поток воспроизведения, и переход к квартире станет переписыванием, а не расширением.

**Арбитраж** (нужен позже, интерфейс — сейчас). Несколько микрофонов слышат одну фразу, отвечать должен один. Окно сбора 200–300 мс после первого срабатывания, выигрывает эндпоинт с наибольшим скором (энергия речи × уверенность детектора), остальные подавляются. На десктопном этапе эндпоинт один и арбитраж — no-op.

**Приоритет по присутствию.** Правило «если я за компьютером — работает компьютер» выражается так: эндпоинт с недавней активностью пользователя выигрывает у комнатных. Сигнал для десктопа — idle-время сессии через `systemd-logind` (свойство `IdleHint`) плюс состояние блокировки экрана. Сейчас читается, но ни на что не влияет; плюмбинг делается сразу, чтобы политике потом было что читать.

#### Три проблемы десктопного эндпоинта

**1. Устройство по умолчанию меняется на ходу.** Подключили наушники, поднялся Bluetooth, приложение переключило выход. `cpal` перечисляет устройства, но не следит за сменой умолчания — нужна подписка на метаданные PipeWire (`default.audio.source` / `default.audio.sink`) через `pipewire-rs`. Поток воспроизведения без явной цели следует за умолчанием сам, но знать текущее устройство всё равно необходимо — см. пункт 2.

**2. Наушники и колонки — разное поведение, а не разная настройка.**

| Вывод | Эхо | AEC | Barge-in |
|---|---|---|---|
| Наушники / гарнитура | нет | выключен | тривиален |
| Колонки | есть | обязателен | требует AEC |

Класс устройства определяется по свойствам узла (`device.form_factor`, `port.type`). Переключение автоматическое, по факту смены устройства вывода, без участия пользователя.

**3. Микрофон разделяемый.** Созвон в Zoom, Meet или Discord за рабочим компьютером — обычное дело. Nana в это время слышит и собеседников, и реплики пользователя, адресованные людям. Политика: при обнаружении чужого потока захвата на том же источнике (PipeWire показывает клиентов узла) Nana не отключает захват, но **поднимает порог активации** — требует wake-word даже в окне продолжения и отключает быстрый путь. Полное отключение на время созвона — опция конфигурации.

#### AEC: внутри процесса, а не модулем PipeWire

Пересмотр раннего решения. Nana сама генерирует свой звук, значит опорный сигнал у неё уже есть — точный, без задержки маршрутизации. Внутрипроцессный AEC (`webrtc-audio-processing`) с собственным render-потоком в качестве опоры проще, чем перестраивать цепочку `module-echo-cancel` при каждой смене устройства по умолчанию.

Ограничение честное: так гасится голос Nana, но не музыка из стороннего приложения. Если замеры Фазы 0 покажут, что музыка ломает распознавание, добавляется второй режим — AEC по монитору вывода, гасящий всё, что звучит из колонок. На наушниках оба режима выключены.

#### Следствие для метрик

Ближнее поле (0.3–1 м) — самый лёгкий акустический случай: выше точность ASR, ниже FAR детектора, заметно надёжнее эмбеддинг говорящего.

Отсюда предупреждение, которое нужно держать в голове до самого перехода к квартире: **пороги, откалиброванные на десктопе, не переносятся на дальнее поле.** Критерии Фаз 3 и 5b относятся к десктопному эндпоинту; комнатные эндпоинты потребуют отдельного прохода калибровки со своими числами.

## 4. Детали, определяющие качество

### 4.1 Кольцевой буфер и pre-roll

Детектор wake-word срабатывает через 200–500 мс после начала слова, а пользователь почти всегда произносит команду слитно с именем. Если начать запись с момента срабатывания, потеряется начало команды.

Решение: постоянный кольцевой буфер на 3 секунды. При срабатывании в ASR уходит отрезок, начинающийся за 1.5 с **до** момента детекции. ASR отдаёт текст целиком, а имя вырезается из начала транскрипта строковым правилом, а не по времени.

### 4.2 Размеры кадров

Три потребителя требуют разных окон, поэтому кольцевой буфер отдаёт срезы, а не поток:

| Потребитель | Окно | Примечание |
|---|---|---|
| AEC | 10–20 мс | WebRTC-совместимый размер |
| Silero VAD | 512 сэмплов (32 мс) @ 16 кГц | фиксировано моделью |
| wake-word | шаг 80 мс (1280 сэмплов) | общий mel-фронтенд с VAD, чтобы не считать мел дважды |
| ASR | отрезок реплики целиком либо чанки 1–2 с | |

Точные значения подтвердить на интеграции — модели обновляются.

### 4.3 Endpointing

Фиксированный порог тишины — главная скрытая потеря времени. Делаем адаптивный:

```
базовый порог                     : 500 мс
реплика совпала с быстрой грамматикой : 250 мс
частичный транскрипт обрывается на союзе/предлоге («и», «чтобы», «на»)
                                  : 900 мс
пауза после заполнителя («эээ», «ну») : 900 мс
жёсткий потолок реплики           : 12 с
минимальная длина реплики         : 300 мс (иначе игнор)
```

Список «незавершённых» окончаний ведём отдельно для русского и английского. Порог — конфигурируемый параметр, подбирается на реальных записях в Фазе 2.

### 4.4 Чанкинг LLM → TTS

Токены нельзя отдавать в TTS по одному: рушится просодия. Правило выпуска чанка:

- **Первый чанк** (минимизируем TTFA): первый терминатор предложения, либо граница клаузы при длине буфера ≥ 40 символов, либо 80 символов.
- **Последующие чанки** (максимизируем просодию): терминатор предложения, либо граница клаузы при длине ≥ 80, либо 200 символов.
- Конец стрима — выпустить остаток.

Отправляем в один WebSocket-контекст провайдера (input-streaming), чтобы интонация не рвалась между чанками.

### 4.5 Barge-in

Механика:

1. Во время `Speaking` VAD работает по очищенному AEC сигналу.
2. Триггер — устойчивая речь ≥ 250 мс. Одиночные щелчки, кашель, всплеск ТВ не проходят.
3. По триггеру: остановить воспроизведение, сбросить очередь PCM, закрыть TTS-контекст, отменить SSE-стрим LLM.
4. **Критично:** в историю диалога записывается не то, что модель сгенерировала, а то, что пользователь **успел услышать**. Очередь воспроизведения ведёт учёт проигранных чанков; ассистентская реплика усекается по этой границе, с пометкой «(прервано)».

Без пункта 4 модель считает, что произнесла текст, которого пользователь не слышал, и следующий ответ ссылается на несуществующий контекст.

### 4.6 Окно продолжения и адресность

В `Continuation` микрофон активен без wake-word — значит, любая фраза в комнате может быть принята за команду. Фильтр, три ступени по возрастанию стоимости:

1. VAD: речь ≥ 400 мс.
2. ASR: confidence выше порога, длина транскрипта ≥ 2 слов, нет маркеров чужого разговора.
2b. Говорящий (§6.3): незнакомый голос в окне продолжения почти всегда означает разговор в комнате, а не обращение. Порог адресности для `Unknown` поднимается.
3. LLM: в системном промпте разрешено вернуть служебный ответ `NOT_ADDRESSED`, если реплика явно не обращена к Nana. Тогда Nana молчит и возвращается в `Continuation`, а реплика не попадает в историю.

Окно продлевается на 8 с после каждого успешного обмена. Жёсткий потолок непрерывного диалога — 5 минут, дальше требуется wake-word.

### 4.7 Нормализация текста перед синтезом

Отдельный модуль с корпусом тестов. Даёт для естественности больше, чем смена провайдера.

| Класс | Пример входа | Выход |
|---|---|---|
| Markdown | `**важно**`, `- пункт`, `` `code` `` | вычистить полностью |
| Числа с падежом | «5 кг», «в 3 часа» | «пять килограммов», «в три часа» |
| Время | «10:30», «10:05» | «десять тридцать», «десять ноль пять» |
| Даты | «12.03.2026» | «двенадцатое марта две тысячи двадцать шестого» |
| Сокращения | «т.д.», «т.е.», «см.» | «так далее», «то есть», «сантиметров» |
| Единицы | «−5 °C», «20 км/ч» | «минус пять градусов», «двадцать километров в час» |
| Порядковые | «2-й» | «второй» |
| Технические токены | `RTX 4090`, `HTTP 404` | «эр-ти-экс сорок девяносто», «эйч-ти-ти-пи четыреста четыре» |
| Пути и URL | `/home/user/file.txt`, ссылка | «файл file точка txt», «ссылка» |
| Эмодзи | любые | удалить |

Русское согласование по падежу и роду — основная сложность. Реализуем таблично для закрытого набора единиц измерения плюс общий модуль числительных; редкие случаи покрываем правилами по мере нахождения на реальных ответах.

Профилактика на стороне LLM: системный промпт запрещает markdown, списки, блоки кода, эмодзи и длинные перечисления. Нормализатор — вторая линия обороны, а не первая.

### 4.8 Кэш готовых фраз

Заранее синтезируем и храним на диске ~40 частых реплик: «Готово», «Не расслышала», «Секунду», «Таймер поставлен», «Свет выключен», подтверждения, извинения, тексты режима деградации. Плюс LRU-кэш на диске для любого повторяющегося синтеза.

Ключ кэша: `hash(нормализованный текст, voice_id, модель, версия нормализатора)`. Даёт нулевую латентность быстрому пути и работоспособность без сети.

## 5. Слой LLM

### 5.1 Модель

Основной путь — `claude-haiku-4-5` ($1/$5 за 1M). Решающий фактор: у неё расширенное мышление по умолчанию выключено, а значит минимальный TTFT. У `claude-opus-5` adaptive thinking включён по умолчанию и напрямую бьёт по требованию R2.

Эскалацию на `claude-opus-5` (`effort: "low"`, при необходимости fast mode) **не делаем на старте**. Вводим в Фазе 5 только если телеметрия покажет реальный процент неудовлетворительных ответов, и тогда через явный инструмент `escalate`, который Haiku вызывает сама.

Rust официального SDK Anthropic не имеет — работаем по raw HTTP: `POST /v1/messages`, стрим SSE через `reqwest` + `eventsource-stream`. Это штатный путь.

### 5.2 Структура запроса и кэширование

Порядок рендеринга у API: `tools` → `system` → `messages`. Кэш работает по префиксу, любое изменение байта инвалидирует всё после него. Отсюда раскладка:

```
tools            [стабильно]  определения инструментов
system           [стабильно]  персона + правила устной речи + устойчивые факты профиля
─── cache_control breakpoint ───
messages[0..n]   [изменчиво]  извлечённый контекст памяти + последние N реплик + текущая
```

Правила:
- Ничего изменчивого (время, id запроса, счётчики) выше брейкпоинта.
- Факты профиля перегенерируют кэш при изменении — поэтому обновляем их пакетно, между сессиями, а не по ходу диалога.
- Контроль: `usage.cache_read_input_tokens`. Если ноль на повторных запросах — ищем тихий инвалидатор.
- Открытый вопрос: стандартный TTL кэша 5 минут. При редком использовании кэш истекает между обращениями и TTFT платится полностью. Измерить в Фазе 0 и решить — принять как есть, прогревать, либо взять расширенный TTL.

`max_tokens` держим низким (≈300): страховка от многословия, которое ломает и латентность, и естественность.

### 5.3 Системный промпт: правила устной речи

Ключевой блок, влияющий на R1 сильнее выбора TTS:

- 1–3 предложения в ответе; развёрнутый ответ — только по явной просьбе.
- Никакого markdown, списков, нумерации, блоков кода, эмодзи.
- Числа, единицы и даты — словами, как в живой речи.
- Не зачитывать URL, пути и длинные идентификаторы.
- Отвечать на языке последней реплики пользователя.
- Не начинать с «Конечно!», «Отлично!» и подобных заполнителей.
- Перед вызовом инструмента допускается одна короткая фраза — она маскирует задержку.
- Если реплика не обращена к Nana — вернуть `NOT_ADDRESSED`.

## 6. Инструменты, быстрый путь, разрешения

### 6.1 Быстрый путь в обход LLM

Грамматический маршрутизатор поверх транскрипта, до обращения к модели. Покрывает самые частые команды:

- таймеры: поставить, отменить, спросить остаток
- громкость: тише, громче, выключить звук, установить значение
- воспроизведение: пауза, дальше, назад
- свет: включить, выключить, яркость
- «стоп», «отмена», «который час»

Ответ берётся из кэша фраз, LLM не вызывается вовсе: **end-to-end ≈ 300–500 мс**, и работает без сети. Принцип — консервативность: при малейшей неоднозначности уходим на путь LLM. Метрики, которые ведём с первого дня: доля попаданий в быстрый путь и доля ошибочных маршрутизаций.

### 6.2 Модель разрешений

Разрешение резолвится **двумя измерениями**: кто говорит и насколько рискованно действие. Личность даёт §6.3.

```rust
enum Risk {
    Safe,          // выполняется молча
    Confirm,       // подтверждение, достаточно известного голоса
    Owner,         // только владелец; при высокой уверенности — молча
    OwnerConfirm,  // только владелец с высокой уверенностью + подтверждение всегда
    Denied,        // не существует как инструмент
}

enum Speaker {
    Owner { score: f32 },   // сопоставлен с профилем владельца
    Known { id: SpeakerId, score: f32 },  // зарегистрированный член семьи
    Unknown,                // не сопоставлен ни с кем
}
```

| Risk \ Говорящий | Owner (высокая) | Owner (пограничная) | Known | Unknown |
|---|---|---|---|---|
| Safe | выполнить | выполнить | выполнить | выполнить |
| Confirm | выполнить | подтвердить | подтвердить | отказать |
| Owner | выполнить | подтвердить | отказать | отказать |
| OwnerConfirm | подтвердить | **отказать** | отказать | отказать |
| Denied | — инструмент не существует — |

| Уровень | Примеры |
|---|---|
| Safe | запрос состояния, таймеры, громкость, музыка, свет, погода |
| Confirm | запустить/закрыть приложение, отправить сообщение, климат, разблокировать экран |
| Owner | удаление файлов, отключение самой Nana, изменение своих же разрешений |
| OwnerConfirm | замки и двери, покупки, платежи, отключение сигнализации |
| Denied | произвольная shell-команда, sudo, пакетный менеджер, запрос по произвольному URL |

Обратите внимание на клетку `OwnerConfirm` × «Owner (пограничная)» — там **отказ, а не подтверждение**. Логика: голосовое подтверждение защищает от неверно распознанной или случайной команды, но не от чужого человека, потому что подтверждение приходит по тому же самому каналу. Если личность опознана неуверенно, переспрос ничего не добавляет. Поэтому для верхнего уровня требуется твёрдая идентификация **и** подтверждение, а не одно вместо другого.

Ключевой эффект для исходной проблемы: **телевизор и посторонние в комнате попадают в `Unknown` и отсекаются на уровне `Confirm` и выше автоматически**, без единого уточняющего вопроса.

Уровня, недоступного голосу в принципе, в системе нет — это осознанное решение заказчика. Замки и покупки открываются голосом владельца при обязательном подтверждении. Остаточный риск и компенсирующие меры — ниже.

#### Протокол подтверждения для OwnerConfirm

Обычное «да» для этого уровня не годится: короткое согласие легко выхватывается из фонового разговора и слишком легко произносится случайно. Правила:

1. **Nana повторяет действие с параметрами**, а не спрашивает абстрактно: «Открыть замок входной двери. Подтверди.»
2. **Требуется содержательная фраза, а не междометие.** Принимаются «да, открой», «подтверждаю», «да, купи» — то есть согласие, содержащее глагол действия. Голое «да», «ага», «угу» не принимаются.
3. **Реплика подтверждения сама проходит сопоставление голоса** и должна дать высокую уверенность. Это второй независимый образец, и он же поднимает накопленную идентичность сессии.
4. **Окно подтверждения 10 секунд.** Истекло — действие отменяется молча, повторный запрос требует новой команды.
5. **Barge-in в окне подтверждения запрещён** — нельзя подтвердить то, чего не дослушал.

#### Компенсирующие меры

Раз голос остаётся единственным каналом для замков и покупок, риск смещается с предотвращения на обнаружение и ограничение ущерба:

- **Внеполосное уведомление на телефон при каждом действии уровня `OwnerConfirm`** — не блокирует и не добавляет трения, но владелец узнаёт о происходящем немедленно, даже если сам не давал команды.
- **Потолок ущерба:** лимит суммы на покупку и суточный лимит; сверх лимита — отказ с объяснением, а не подтверждение.
- **Ограничение частоты:** не более N операций с замками в час.
- **Журнал аудита** (§7.1): каждое действие уровня `Owner` и `OwnerConfirm` пишется с временем, скором голоса, транскриптом команды и транскриптом подтверждения. Это то, что позволяет разобраться постфактум.
- **Откат где возможен:** отмена покупки в течение короткого окна голосом же.


Инструменты описываем со `strict: true`, чтобы аргументы гарантированно валидировались по схеме. Параллельные вызовы разрешены, все `tool_result` возвращаются **одним** user-сообщением. Бюджет на исполнение инструмента — 2 с; по таймауту возвращаем ошибку как результат, чтобы модель могла озвучить внятное объяснение.

Авторизация происходит **до** исполнения и **после** того, как модель выбрала инструмент. Отказ возвращается модели как `tool_result` с причиной — она формулирует человеческое объяснение вместо системной ошибки.

### 6.3 Голосовой отпечаток

#### Модель и место в конвейере

Эмбеддинг говорящего снимается **с того же аудио, что уже захвачено для ASR** — дополнительной записи не требуется. Модель: ECAPA-TDNN или CAM++ (3D-Speaker) в ONNX через `ort`, ~20 МБ. Инференс на реплике 2–3 с — порядка 10–30 мс на CPU, выполняется параллельно с ASR.

**Влияние на R2 нулевое.** Это важно: биометрия здесь не стоит ни одной миллисекунды бюджета задержки.

Сегмент wake-word даёт первую оценку личности ещё до окончания команды — используется для предварительного прогрева и для ранней отбраковки явно чужого голоса.

#### Сопоставление и пороги

Косинусная близость к набору эмбеддингов профиля (храним несколько, а не один центроид; скор — среднее по top-k). Два порога вместо одного:

```
score ≥ accept_high  → Owner, высокая уверенность
accept_low ≤ score   → Owner, пограничная уверенность → подтверждение
score < accept_low   → Unknown
```

**Главная проблема — короткие команды.** «Выключи свет» это 1.1 с речи, и эмбеддинг с неё нестабилен. А это ровно те команды, которые чаще всего и нужно авторизовать. Три меры:

1. Ниже 1.5 с речи уверенность принудительно понижается на ступень — короткая реплика не даёт высокого доверия никогда.
2. **Идентичность накапливается на уровне сессии.** Wake-word, реплика, окно продолжения — все сегменты вносят вклад в текущую оценку с затуханием по времени. Второй-третий обмен подряд даёт заметно более надёжную идентификацию, чем первый.
3. Пороги калибруются на реальных записях в Фазе 5, а не берутся из статьи: они зависят от микрофона, расстояния и акустики комнаты.

#### Регистрация

Голосом: «Nana, запомни мой голос». Ведомая процедура — 5 фраз, 15–20 секунд суммарно, содержательно разных.

Обязательное условие: **регистрация с целевого устройства и с рабочей дистанции**. Профиль, снятый с телефона вблизи, не сработает на дальнопольном массиве в трёх метрах — это другой акустический канал.

Инкрементная адаптация: эмбеддинги обменов с очень высокой уверенностью добавляются в профиль, размер набора ограничен, исходная регистрация неизменяема. Ограничения не косметические — без них профиль дрейфует и его можно постепенно отравить.

#### Чего голосовой отпечаток не делает

Разделяет **узнавание** и **аутентификацию**, и надо честно понимать границу.

Защищает надёжно: от случайных команд домашних и гостей, от речи из телевизора и подкастов, от команд из соседней комнаты. Это ровно та проблема, ради которой модель разрешений вводилась.

Не защищает: от воспроизведения записи владельца и от клонирования голоса. В 2026 году клонирование по нескольким секундам аудио — дешёвая и доступная операция.

**Зафиксированное решение:** заказчик принял этот риск для замков и покупок, оставив их на уровне `OwnerConfirm` вместо недоступного голосу уровня. Практически это означает, что убедительный клон голоса владельца, прошедший подтверждение содержательной фразой, откроет замок. Компенсация — обнаружение и ограничение ущерба, а не предотвращение: уведомление на телефон, лимиты, частотное ограничение, журнал аудита. Если позже появится желание закрыть и этот вектор, возвращается уровень с физической кнопкой или подтверждением с телефона — архитектурно это добавление одной строки в `enum Risk` и одного столбца в матрицу.

Детектор подмены класса AASIST (ONNX) добавляем **как слагаемое в скор, а не как шлагбаум**: воспроизведение через колонку он ловит прилично, синтез и клонирование — заметно хуже, и вне условий обучения деградирует.

#### Отказоустойчивость

Голос меняется: болезнь, утро, усталость, простуда. Провал сопоставления не должен превращать ассистента в кирпич.

- Понижение всегда мягкое: `Owner` → подтверждение, а не отказ.
- Аварийный путь: команда с клавиатуры целевой машины или физическая кнопка перекрывает голосовую авторизацию.
- Три неудачных сопоставления подряд для голоса, который ведёт себя как владелец → Nana предлагает переснять профиль.

#### Побочная выгода: персонализация

Это не только про безопасность. Личность говорящего делает **память корректной в доме с несколькими людьми**: «запомни, что я не ем мясо» привязывается к правильному человеку, у каждого свои таймеры, музыка и предпочтения, и Nana обращается по имени. Без идентификации профиль в §7 неизбежно превращается в кашу из фактов разных людей.

Ради этого отдельный уровень `Known` и существует — зарегистрированный член семьи, которому доступно всё бытовое, но не файлы и деньги владельца.

### 6.4 Канал инициативной речи

Компонент `nana-core::proactive`. Источники событий: сработавшие таймеры, будильники, уведомления умного дома.

Политика:
- `Idle` → короткий звуковой сигнал, затем фраза.
- `Listening` / `Thinking` → очередь, произносим после завершения обмена.
- `Speaking` → очередь.
- Событий в очереди несколько → объединяем в одну фразу.
- События старше 10 минут (машина спала, пользователя не было) — не озвучиваем, а помечаем как пропущенные.

## 7. Память

### 7.1 Схема SQLite

```sql
sessions(id, started_at, ended_at, lang)
turns(id, session_id, ts, role, text, lang, asr_conf, route, latency_ms,
      in_tokens, out_tokens, cost_usd, barged_in,
      speaker_id, speaker_score)
speakers(id, name, role, enrolled_at, updated_at)   -- role: owner | known
voiceprints(id, speaker_id, embedding BLOB, source, created_at, immutable)
facts(id, speaker_id, key, value, confidence, source_turn, created_at, updated_at)
summaries(session_id, text, created_at)
audit(id, ts, speaker_id, speaker_score, risk, tool, args_json,
      command_text, confirm_text, outcome)   -- уровни Owner и OwnerConfirm
turns_fts  -- FTS5 по turns.text
```

`rusqlite` со сборкой bundled и FTS5. Одна база, файл с правами 0600.

`facts` и извлечение контекста **фильтруются по `speaker_id`**: каждый обмен видит факты текущего говорящего плюс общедомовые (`speaker_id IS NULL`). Без этого в доме с несколькими людьми профиль превращается в противоречивую смесь.

### 7.2 Извлечение контекста

Гибридное, без эмбеддингов на старте:

1. Последние N реплик текущей сессии дословно (N ≈ 8, с ограничением по токенам).
2. Все факты профиля — они компактны и живут в кэшируемой части промпта.
3. Поиск по FTS5 по существительным из текущей реплики → до 3 релевантных фрагментов прошлых диалогов.
4. Саммари предыдущей сессии, если текущая началась меньше суток назад.

Эмбеддинг-поиск добавляем позже и только при доказанной нехватке FTS5: он тянет ещё одну модель на горячий путь.

### 7.3 Извлечение фактов

**Строго вне горячего пути.** После завершения обмена в фоновую очередь ставится задача: дешёвый вызов Haiku, который вытаскивает из пары «реплика-ответ» устойчивые факты (имена, предпочтения, расписание, названия устройств). Результат пишется в `facts` с дедупликацией по ключу.

Ни одна миллисекунда этой работы не попадает в измеряемую задержку ответа.

### 7.4 Приватность

- Сырое аудио не сохраняется никогда по умолчанию. Отладочный кольцевой буфер на диск — только по явному флагу конфигурации, с автоочисткой.
- Аппаратный или горячий-клавишный mute, полностью останавливающий захват, с видимой индикацией состояния.
- Голосовые команды «забудь это», «удали историю за сегодня», «что ты обо мне знаешь».
- Настраиваемая политика хранения истории (по умолчанию — 90 дней).
- **Голосовые отпечатки — биометрические данные.** Хранятся только локально, в облако не уходят ни при каких условиях, шифруются на диске. Команды «удали мой голосовой профиль» и «кого ты знаешь» обязательны. Регистрация нового человека — только с явного согласия, молча по ходу разговора профили не создаются.
- Ключи API: `~/.config/nana/secrets.toml` с правами 0600 либо переменные окружения. В git не попадают ни при каких условиях.

## 8. Устойчивость и деградация

### 8.1 Сторож задержки

Таймер на каждый обмен:

- **T+2.5 с** без единого проигранного сэмпла → воспроизвести заполнитель из кэша («Секунду...»).
- **T+6 с** → одна повторная попытка запроса.
- **T+9 с** → прервать, извиниться заранее записанной фразой, вернуться в `Idle`.

Худший сценарий для пользователя — не медленный ответ, а глухая тишина. Сторож её исключает.

### 8.2 Матрица деградации

| Отказ | Поведение |
|---|---|
| Нет сети | Локальный TTS (Silero/Piper), доступен только быстрый путь. «Я сейчас без интернета — могу поставить таймер и управлять светом» |
| LLM недоступна | То же, плюс явное сообщение о проблеме |
| TTS недоступна | Переключение на локальный TTS на ходу. Голос меняется — это заметно, но лучше молчания |
| ASR низкая уверенность | «Не расслышала, повтори?» |
| Аудиоустройство исчезло (USB) | Переподключение с backoff, состояние `Degraded`, лог |
| Инструмент упал | Результат с ошибкой уходит в модель, она формулирует внятное объяснение |

Все реплики режима деградации — в предсинтезированном кэше, иначе они недостижимы ровно тогда, когда нужны.

## 9. Телеметрия

Запись на каждый обмен, в SQLite:

```
turn_id, session_id, route (fastpath|llm|proactive)
wake_ts, speech_start_ts, speech_end_ts
asr_first_partial_ms, asr_final_ms, asr_conf, lang
llm_ttft_ms, llm_done_ms, tool_calls[{name, ms, ok}]
tts_first_chunk_ms, playback_start_ms, playback_done_ms
barged_in, watchdog_fired
cache_read_tokens, in_tokens, out_tokens, cost_usd
```

`nana-cli stats` печатает p50/p95 по каждой стадии за период. Встраивается в Фазе 1, не позже: прикрутить телеметрию задним числом к асинхронному конвейеру дороже, чем заложить сразу, а без неё оптимизация задержки превращается в гадание.

## 11. Wake-word: план по «Nana»

Акустический триггер — **«Хей, Нана»** и **«Hey Nana»** (две модели, обе активны). Односложно-короткое «Нана» даёт неприемлемый уровень ложных срабатываний, особенно на русской речи, где сочетание встречается внутри слов.

Обучение: синтетический корпус (Piper во множестве голосов) + аугментация импульсными характеристиками помещений и шумом. Негативные примеры — подкасты, ТВ, фоновая речь на обоих языках.

Приёмка: FRR < 5 % при FAR < 0.5/час, измеряется на **реальной записи комнаты**, включая работающий телевизор, а не на синтетике.

Вторая ступень (верификация фразы через ASR по pre-roll) включена по умолчанию; отключается конфигом, если измерения покажут, что первая ступень достаточно точна.

## 12. Требования к целевой машине

| Уровень | Конфигурация | Что даёт |
|---|---|---|
| A — рекомендуемый | 8 ядер, 32 ГБ RAM, NVIDIA RTX 4060/5060 (8–12 ГБ) | Whisper large-v3-turbo ≈ 0.2 с на 5 с речи; запас под локальный TTS |
| B — бюджетный | Mini-PC без дискретной GPU | Whisper turbo/small на CPU 0.8–1.5 с; в бюджет R2 укладывается |
| C — полностью локальный (на будущее) | RTX 4090/5090, 24–32 ГБ VRAM | локальная LLM + CosyVoice2 |

**Аудио на десктопном этапе** покупать не нужно: используется системный микрофон по умолчанию и текущее устройство вывода. Это и есть смысл решения R10 — первый рабочий контур собирается на том, что уже стоит на столе.

Остальное:

- **Тишина корпуса.** Вентилятор рядом с микрофоном ухудшает распознавание и провоцирует ложные срабатывания VAD. Пассивное охлаждение или тихий корпус.
- Проводная сеть предпочтительнее Wi-Fi: джиттер напрямую входит в бюджет задержки.
- **К многокомнатному этапу** понадобятся дальнопольные массивы (ReSpeaker Mic Array v2 и подобные) на каждую зону. Там микрофон действительно важнее видеокарты, но это уже следующий разговор — на десктопе ближнее поле снимает проблему.

## 13. Стоимость

Порядок величин на один обмен:

| Статья | Оценка |
|---|---|
| LLM (Haiku 4.5, с кэшем промпта, ответ ~120 токенов) | ~$0.001 |
| TTS (~300 символов) | ~$0.015 |
| ASR (локально) | $0 |

**Драйвер расходов — синтез речи, а не модель**, примерно на порядок. Отсюда практические следствия: кэш готовых фраз окупается не только латентностью; жёсткий лимит `max_tokens` экономит вдвойне; при росте нагрузки экономически оправдан переход на локальный TTS, а не на более дешёвую LLM.

Ориентир: 100 обменов в день ≈ $1.6/день ≈ **$50/месяц**. Тарифы TTS-провайдеров подтвердить в Фазе 0 — они меняются.

## 15. Открытые вопросы

1. ~~**Аудиотопология.**~~ Закрыто решением R10: десктопный эндпоинт первым, системный микрофон по умолчанию и текущее устройство вывода. Многокомнатная схема — расширение через `trait Endpoint` (§3.4). **Фаза 0 разблокирована.** Оставшиеся подвопросы: нужен ли режим AEC по монитору вывода (решается замером с играющей музыкой) и когда включать приоритет эндпоинта по присутствию.
2. **Провайдер TTS.** Решается измерением в Фазе 0. Кандидаты: ElevenLabs Flash v2.5 (подтверждённый русский, ~288 мс), Inworld Realtime TTS-2 (заявлено <100 мс, 200+ языков), Cartesia Sonic-3 (быстрейший, поддержку русского нужно проверить руками).
3. **Голос Nana.** Один `voice_id` на мультиязычной модели — иначе по-русски и по-английски говорят разные люди, а смешанные фразы разваливаются. Выбор — слепым прослушиванием в Фазе 0.
4. **TTL кэша промпта** при редком использовании (§5.2).
5. **Интеграция умного дома:** Home Assistant REST, MQTT или прямые API устройств.
6. **Источник музыки:** локальный MPD, Spotify Connect, YouTube Music.
7. **Детектор подмены (AASIST)** — включаем в Фазе 5b или откладываем: на уровне `Critical` голос всё равно не принимается, поэтому выгода в основном на уровне `Owner`.
8. **Лимиты для `OwnerConfirm`** — сумма покупки, суточный потолок, частота операций с замками. Численные значения задаются, когда станет известен состав устройств и платёжных интеграций.
9. **Сколько человек регистрируем** — только владелец или вся семья с уровнем `Known`. Влияет на калибровку порогов: чем больше профилей, тем выше требования к разделимости.
